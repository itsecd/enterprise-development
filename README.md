# Отчет по лабораторной работе №3: Entity Framework Core, MySQL и .NET Aspire

## Цель работы
Перевод слоя хранения данных ветеринарной клиники с оперативной памяти на реляционную СУБД **MySQL** с использованием ORM **Entity Framework Core**, автоматизация оркестрации контейнеров через **.NET Aspire** и реализация сквозных интеграционных тестов.

## Обновленная архитектура решения

Благодаря соблюдению принципа инверсии зависимостей (DIP) во второй лабораторной работе, перенос приложения на реляционную базу данных выполнен без изменения бизнес-логики (`Application`), контрактов (`Application.Contracts`) и контроллеров (`Api.Host`). В решение добавлены инфраструктурный слой БД и проекты оркестрации:

*   **VetClinic.Domain:** Сущности домена (`Pet`, `Vet`, `Owner`, `Appointment` и др.), перечисления (`Species`, `RepeatVisitIndicator`), интерфейсы репозиториев и перенесенный эталонный датасет `VetClinicDataSeeder`.
*   **VetClinic.Application.Contracts:** Плоские структуры обмена данными на базе C# `record` (`PetDto`, `PetCreateUpdateDto`) и интерфейсы прикладных сервисов.
*   **VetClinic.Application:** Прикладные сервисы маппинга и аналитический сервис `AnalyticService`.
*   **VetClinic.EFCore:** Контекст `VetClinicDbContext`, конфигурация Fluent API, миграции (`InitialCreate`), фабрика времени разработки `VetClinicDbContextFactory` и EF Core репозитории.
*   **VetClinic.AppHost:** Точка входа для развертывания распределенного приложения, автоматического поднятия Docker-контейнера MySQL и управления зависимостями между сервисами.
*   **VetClinic.ServiceDefaults:** Общие политики отказоустойчивости (Resilience), телеметрия (OpenTelemetry) и проверки состояния (Health Checks).
*   **VetClinic.Api.Host (Web-уровень):** REST-контроллеры, автоматическое применение миграций при запуске, сериализация `Enum` в строки и документация Scalar UI.
*   **VetClinic.Tests (Интеграционное тестирование):** Фикстура `VetClinicAspireFixture` и сквозные интеграционные тесты xUnit v3.

## Ключевые архитектурные и технические решения

### 1. Конфигурация схемы БД и Seeding (`VetClinicDbContext`)
В методе `OnModelCreating` настроена реляционная модель для MySQL:
*   **Внешние ключи и целостность данных:** Настроены связи один-ко-многим; справочники (породы, специализации, врачи, услуги) защищены от случайного удаления через `DeleteBehavior.Restrict`, а для зависимостей «Владелец — Питомец — Прием» задано каскадное удаление `DeleteBehavior.Cascade`.
*   **Типы данных MySQL:** Задана точная размерность для денежных полей (`HasPrecision(10, 2)` для стоимости услуг) и строковое хранение перечислений (`HasConversion<string>()`).
*   **Начальное наполнение (`HasData`):** Эталонные данные из `VetClinicDataSeeder` интегрированы в миграцию `InitialCreate` с обнулением навигационных свойств для соблюдения требований EF Core.

### 2. Репозитории EF Core и управление загрузкой данных
*   **Жадная загрузка:** В методах чтения (`GetAll`, `Get`) использованы цепочки `.Include()` и `.ThenInclude()` для подгрузки связанных сущностей (`Breed`, `Owner`, `Specialization`, `Pet`, `Vet`, `Service`), исключая проблему N+1 и `NullReferenceException` при маппинге в DTO.
*   **Предотвращение дублирования сущностей:** В методах создания (`Create`) навигационные ссылки принудительно зануляются перед `SaveChangesAsync()`, чтобы EF Core привязывал новые записи исключительно по внешним ключам (`BreedId`, `OwnerId`, `VetId` и др.).

### 3. Оркестрация контейнеров и авто-миграции (.NET Aspire)
*   В `AppHost.cs` описано развертывание сервера **MySQL** с постоянным томом данных (`WithDataVolume()`) и базы `vetclinicdb`. Веб-сервер `vetclinic-api` ожидает полной готовности СУБД (`WaitFor(vetDb)`) перед запуском.
*   В `VetClinic.Api.Host` подключение к БД инкапсулировано в методе расширения `AddEfCoreDataLayer("vetclinicdb")`. При старте сервера автоматически выполняется `await dbContext.Database.MigrateAsync()`, разворачивая таблицы и начальные данные без ручного вмешательства.

### 4. Сквозные интеграционные тесты (`Aspire.Hosting.Testing`)
Вместо проверки коллекций в оперативной памяти реализовано тестирование реального стека в Docker:
*   Фикстура `VetClinicAspireFixture` однократно запускает `VetClinic.AppHost`, дожидается статуса `Healthy` от API (`WaitForResourceHealthyAsync`) и предоставляет настроенный `HttpClient`.
*   Тесты проверяют чтение начального сидера, полный жизненный цикл сущности в БД, обработку несуществующих внешних ключей и выполнение всех 5 аналитических запросов поверх SQL-таблиц.

## Запуск приложения и тестов

*   **Требования:** Установленный и запущенный **Docker Desktop** (на движке WSL 2).
*   **Запуск системы и Aspire Dashboard:** Назначьте стартовым проектом **`VetClinic.AppHost`** и нажмите **F5**. После перехода ресурсов `mysql` и `vetclinic-api` в статус `Running` откройте интерфейс **Scalar UI** по адресу эндпоинта API с суффиксом `/scalar/v1`.
*   **Запуск интеграционных тестов:** Остановите отладку приложения и выполните прогон в **Обозревателе тестов** Visual Studio (**Ctrl + E, T**) или командой `dotnet test`.
