# DryCleaning — лабораторная работа № 4 «Инфраструктура»

Курс «Разработка корпоративных приложений». REST API для химчистки на ASP.NET Core и .NET 10. Данные хранятся в MS SQL Server и читаются через Entity Framework Core. Отдельный сервис-генератор создаёт заказы и передаёт их серверу через Apache Kafka. Сервер, генератор, база данных и брокер запускаются оркестратором Aspire.

Интерфейсы репозиториев находятся в Domain, а их реализации — в Infrastructure.EfCore. Во второй лабораторной работе репозитории хранили данные в памяти; при переходе на базу данных заменились реализации репозиториев, а сервисы и контроллеры продолжили работать с теми же интерфейсами.

Перечисления вынесены из Domain в отдельный проект Domain.Shared. Contracts теперь ссылается только на него, поэтому генератор, которому нужны контракты, не получает ссылок на Domain и остальные серверные проекты.

## База данных

Модель базы описана в `DryCleaningDbContext` и четырёх классах конфигурации — по одному на сущность.

| Таблица | Ключ | Внешние ключи |
|---|---|---|
| `Clients` | `ClientId` | — |
| `ItemCategories` | `CategoryId` | — |
| `Items` | `ItemId` | `CategoryId` → `ItemCategories` |
| `Orders` | `Id` | `ClientId` → `Clients`, `ItemId` → `Items` |

- Ключи генерирует SQL Server (`IDENTITY`).
- Длины строк совпадают с ограничениями входных DTO: `nvarchar(100)` для имени клиента, названия и материала изделия, `nvarchar(20)` для телефона, `nvarchar(50)` для названия категории. Цена хранится как `decimal(18,2)`.
- Внешние ключи объявлены в доменных классах явно: `Order.ClientId`, `Order.ItemId` и `Item.CategoryId`. Навигационные свойства (`Order.Client`, `Order.Item`, `Item.Category`) нужны только для чтения связанных данных. При создании и изменении записей связь задаётся ключом, поэтому связанные сущности не нужно загружать и отслеживать.
- Для всех связей задано `DeleteBehavior.Restrict` (`ON DELETE NO ACTION`): база не даст удалить клиента или изделие с заказами либо категорию с изделиями.
- Даты хранятся в UTC. При чтении конвертер помечает их как `DateTimeKind.Utc`, поэтому API возвращает даты с суффиксом `Z`.

Миграция `Initial` создаёт таблицы и заполняет их данными из `TestData` через `HasData`: 10 клиентов, 10 категорий, 20 изделий и 20 заказов. В режиме Development API применяет недостающие миграции при запуске.

Репозитории загружают связанные данные через `Include`: изделия — вместе с категорией, заказы — вместе с клиентом, изделием и категорией изделия (`ThenInclude`). Если база отклоняет операцию из-за связанных данных (например, связанная запись удалена одновременно с запросом), контроллер возвращает `409 Conflict`.

Новая миграция создаётся из папки `DryCleaning` командой:

```powershell
dotnet ef migrations add <Название> --project src/DryCleaning.Infrastructure.EfCore --output-dir Data/Migrations
```

## Генератор и обмен через Kafka

`DryCleaning.Generator` — отдельное приложение. Из проектов решения оно ссылается только на Contracts и ServiceDefaults.

Путь заказа от генератора до базы:

1. `OrderGenerator` с помощью Bogus создаёт `OrderCreateDto`: клиент 1–12, изделие 1–22, срок обработки 1–14 дней. В начальных данных клиенты 1–10 и изделия 1–20, поэтому часть заказов ссылается на несуществующие записи и сервер их отклоняет.
2. `OrderGeneratorService` — фоновая служба. Она собирает пачку заказов, передаёт её отправителю и ждёт паузу. После отправки заданного общего количества служба останавливается.
3. `KafkaOrderProducer` отправляет пачку одним сообщением в топик `drycleaning-orders`. Значение сообщения — JSON-массив заказов, ключ не используется.
4. На сервере фоновая служба `OrderKafkaConsumer` читает сообщение, создаёт область зависимостей и передаёт каждый заказ в `IOrderService.AddAsync`. Это тот же метод, который вызывает `POST /api/orders`, поэтому заказы из Kafka проходят те же проверки, что и заказы из HTTP-запросов.

Заказ, не прошедший проверку (нет клиента или изделия, срок не больше нуля), пропускается с предупреждением в логе. Остальные заказы пачки сохраняются. На новой базе проверку проходят примерно три заказа из четырёх.

Настройки:

| Настройка | Где задана | Значение |
|---|---|---|
| Топик | `Parameters:KafkaTopic` в `appsettings.json` AppHost | `drycleaning-orders` |
| Группа потребителей | `Parameters:KafkaConsumerGroup` там же | `drycleaning-api` |
| Размер пачки | `Parameters:GeneratorBatchSize` там же | 5 |
| Всего заказов за запуск | `Parameters:GeneratorPayloadLimit` там же | 30 |
| Пауза между пачками, с | `Parameters:GeneratorWaitTime` там же | 2 |
| Попыток отправки пачки | `Kafka:MaxAttempts` в `appsettings.json` генератора | 5 |
| Первая пауза между попытками, с | `Kafka:RetryDelay` там же | 2 |

Настройки генератора проверяются при запуске: с пустым или неположительным значением приложение не стартует.

### Повторные попытки

Одна попытка отправки пачки длится не дольше 5 секунд (`MessageTimeoutMs`). Если брокер за это время не принял сообщение, генератор пишет предупреждение в лог, ждёт и пробует снова. Пауза после каждой неудачи удваивается: 2, 4, 8, 16 секунд. После пятой неудачной попытки генератор пишет ошибку и завершает работу.

Потребитель на сервере отдельного счётчика попыток не имеет. Клиент Kafka переподключается к брокеру сам, а при ошибке чтения служба ждёт 2 секунды и продолжает. Пока брокер недоступен, API работает как обычно. Если чтение прервётся из-за неустранимой ошибки, служба запишет её в лог и остановится, а API продолжит отвечать на запросы.

Ограничения текущей реализации:

- Гарантия доставки — «как минимум один раз». Если брокер принял сообщение, а подтверждение не дошло, пачка будет отправлена повторно и заказы продублируются.
- Потребитель фиксирует смещения автоматически. Если при сохранении пачки произошла ошибка базы данных, оставшиеся заказы этой пачки не сохраняются и повторно не читаются.
- Каждый запуск оркестратора добавляет в базу новые заказы, потому что генератор стартует заново, а база постоянная.

## Оркестрация

`DryCleaning.AppHost` описывает шесть ресурсов:

| Ресурс | Что это |
|---|---|
| `sql` | Контейнер MS SQL Server. Контейнер постоянный (`ContainerLifetime.Persistent`), данные хранятся в томе Docker и сохраняются между запусками |
| `drycleaning` | База данных внутри `sql` |
| `drycleaning-kafka` | Контейнер Apache Kafka. Создаётся заново при каждом запуске, сообщения между запусками не сохраняются |
| `kafka-ui` | Веб-интерфейс для просмотра топиков и сообщений |
| `api` | Проект `DryCleaning.Api` |
| `generator` | Проект `DryCleaning.Generator` |

API получает строку подключения через `WithReference(db)` — в переменной окружения `ConnectionStrings__drycleaning` — и запускается только после готовности базы (`WaitFor(db)`). Контекст регистрируется клиентской интеграцией Aspire `AddSqlServerDbContext`. `DryCleaning.ServiceDefaults` подключает проверки состояния и телеметрию, поэтому логи, трассировки и метрики API и генератора видны в дашборде Aspire.

Адрес брокера API и генератор получают так же, через `WithReference(kafka)`, и запускаются после его готовности. Продюсер и потребитель регистрируются клиентской интеграцией Aspire: `AddKafkaProducer` и `AddKafkaConsumer`. Имя топика, группу потребителей и настройки генерации AppHost передаёт проектам через переменные окружения из своих параметров.

## DTO и проверки данных

| Сущность | Ответ API | Создание | Изменение |
|---|---|---|---|
| Клиент | `ClientDto` | `ClientEditDto` | `ClientEditDto` |
| Категория | `ItemCategoryDto` | `ItemCategoryEditDto` | `ItemCategoryEditDto` |
| Изделие | `ItemDto` | `ItemEditDto` | `ItemEditDto` |
| Заказ | `OrderDto` | `OrderCreateDto` | `OrderEditDto` |

DTO заказа содержит `ClientDto` и `ItemDto`, а DTO изделия — `ItemCategoryDto`. Доменные сущности из API не возвращаются.

Входные DTO используют атрибуты валидации. Имя клиента ограничено 100 символами, телефон — 20 символами и проверяется атрибутом `[Phone]`. Название категории ограничено 50 символами, цена должна быть больше нуля и не превышать 10 000 000. Название и материал изделия ограничены 100 символами. Идентификаторы связанных записей и плановый срок обработки должны быть положительными, виды обработки и статусы — допустимыми значениями enum.

Существование связанных записей, запреты удаления и соответствие даты завершения статусу заказа проверяются в сервисах. Ошибки выполнения операций записываются через `ILogger`; при неожиданной ошибке контроллер возвращает `500` без внутренних деталей исключения.

## REST API

Для каждой сущности доступны `GET` списка, `GET` по ID, `POST`, `PUT` по ID и `DELETE` по ID.

| Сущность | Список и создание | Получение, изменение и удаление по ID |
|---|---|---|
| Клиенты | `/api/clients` | `/api/clients/{id}` |
| Категории | `/api/categories` | `/api/categories/{id}` |
| Изделия | `/api/items` | `/api/items/{id}` |
| Заказы | `/api/orders` | `/api/orders/{id}` |

Заказы ссылаются на существующих клиентов и изделия, а изделия — на существующие категории. Нельзя удалить клиента или изделие с заказами либо категорию с изделиями: сервер возвращает `409 Conflict`. Для некорректных данных используется `400 Bad Request`, для отсутствующей записи — `404 Not Found`. Успешное создание возвращает `201 Created`, а изменение и удаление — `204 No Content`.

Новый заказ получает статус `Accepted` и время приёма в UTC. При изменении заказа дата завершения обязательна для статусов `Completed` и `Issued`, а для остальных статусов должна быть пустой. Передаваемая дата завершения должна содержать `Z` или смещение часового пояса и не может быть раньше даты приёма.

Для получения связанных записей доступны:

- `GET /api/clients/{clientId}/orders` — заказы клиента;
- `GET /api/categories/{categoryId}/items` — изделия категории.

Если клиент или категория существуют, но связанных записей нет, возвращается `200 OK` с пустым массивом. Если клиент или категория не найдены — `404 Not Found`.

## Аналитические запросы

| Маршрут | Результат на исходных данных |
|---|---|
| `GET /api/orders/in-progress` | Заказы в обработке, отсортированные по дате приёма: ID 1, 12, 9 |
| `GET /api/clients/top?start=2025-09-15&end=2026-09-15` | Пять клиентов по числу принятых изделий: ID 1, 2, 3, 4, 5; количества 4, 4, 3, 2, 1 |
| `GET /api/clients/top-spender` | Клиент 2, сумма выданных заказов 6700 |
| `GET /api/clients/longest-processing` | Клиенты 1 и 4, максимальная длительность 19 дней |
| `GET /api/categories/popularity?end=2026-03-01` | Наиболее популярные категории: ID 8, 3, 6, 4, 1; наименее популярные: ID 2, 9, 3, 6, 4 |

Результаты получены на данных, которыми миграция заполняет базу. В запросах за период начальная дата включается, конечная — нет. Для рейтинга клиентов параметры `start` и `end` обязательны; отсутствие любого из них возвращает `400 Bad Request`. Отменённые заказы не участвуют в рейтингах клиентов и категорий. Категории без заказов участвуют в рейтинге наименее популярных. Расходы клиента считаются по текущей цене категории изделия.

## Запуск и проверка

Требуются .NET SDK 10 и запущенный Docker Desktop. Из папки `DryCleaning` запустить оркестратор:

```powershell
dotnet run --project .\src\DryCleaning.AppHost
```

В Visual Studio можно открыть [DryCleaning.slnx](DryCleaning.slnx), выбрать `DryCleaning.AppHost` запускаемым проектом и нажать F5.

В консоли появится ссылка для входа в дашборд Aspire. При первом запуске Docker скачивает образы SQL Server и Kafka, это занимает несколько минут. Когда все ресурсы перейдут в состояние Running, API доступен по ссылке из дашборда (`https://localhost:3622`). Swagger UI находится по адресу `https://localhost:3622/swagger`, описание OpenAPI — `https://localhost:3622/openapi/v1.json`.

Для ручной проверки открыть [DryCleaning.Api.http](src/DryCleaning.Api/DryCleaning.Api.http). Там собраны успешные запросы и примеры ошибок. Запросы на изменение и удаление созданных записей используют идентификаторы 11 и 21: их получают первые записи, созданные на новой базе. Если база уже использовалась, в этих запросах нужно подставить идентификатор из ответа на `POST`. Для заказов это нужно делать всегда: генератор создаёт заказы раньше, чем дойдёт очередь до ручных запросов.

### Проверка обмена через Kafka

После запуска оркестратора:

1. В логах `generator` в дашборде шесть строк «Пачка из 5 заказов отправлена в топик drycleaning-orders» и в конце «Генератор завершил работу: отправлено 30 заказов».
2. В Kafka UI (ссылка у ресурса `kafka-ui`) в топике `drycleaning-orders` шесть сообщений с JSON-массивами заказов.
3. В логах `api` на каждую пачку строки «Получена пачка из 5 заказов» и «Пачка обработана: сохранено N, пропущено M». Для отклонённых заказов есть предупреждения «Заказ пропущен: Клиент не найден» или «Заказ пропущен: Изделие не найдено».
4. `GET /api/orders` возвращает новые заказы со статусом `Accepted` (0) и текущей датой приёма. Их столько, сколько в сумме сохранено по логам `api`.

Чтобы увидеть повторные попытки, генератор должен работать дольше: в `appsettings.json` AppHost увеличить `GeneratorPayloadLimit`, например до 300. Затем во время работы генератора остановить контейнер Kafka и через 10–15 секунд запустить снова:

```powershell
docker ps --format "{{.Names}}"
docker stop <имя контейнера drycleaning-kafka-...>
docker start <имя контейнера drycleaning-kafka-...>
```

В логах генератора появятся строки «Не удалось отправить пачку… Попытка 1 из 5, следующая через 2 с», а после возврата брокера отправка продолжится.

Для запуска пяти тестов xUnit v3 из той же папки:

```powershell
dotnet test .\DryCleaning.slnx
```

Тесты проверяют аналитические LINQ-запросы на фиксированном наборе данных `TestData`. Им не нужны база данных и Docker.
