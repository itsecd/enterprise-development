# DryCleaning — лабораторная работа № 3 «ORM»

Контроллеры получают интерфейсы сервисов через конструктор и работают с DTO. Сервисы проверяют данные, выполняют бизнес-правила и аналитические запросы, обращаются к репозиториям и преобразуют доменные объекты в DTO.

Интерфейсы репозиториев находятся в Domain, а их реализации — в Infrastructure.EfCore. Во второй лабораторной работе репозитории хранили данные в памяти; при переходе на базу данных заменились реализации репозиториев, а сервисы и контроллеры продолжили работать с теми же интерфейсами.

## База данных

Модель базы описана в `DryCleaningDbContext` и четырёх классах конфигурации — по одному на сущность.

| Таблица | Ключ | Внешние ключи |
|---|---|---|
| `Clients` | `ClientId` | — |
| `ItemCategories` | `CategoryId` | — |
| `Items` | `ItemId` | `CategoryId` → `ItemCategories` |
| `Orders` | `Id` | `ClientId` → `Clients`, `ItemId` → `Items` |

- Ключи генерирует SQL Server (`IDENTITY`).
- Длины строк совпадают с ограничениями входных DTO: `nvarchar(100)` для имени клиента, названия и материала изделия, `nvarchar(20)` для телефона, `nvarchar(50)` для названия категории. Цена хранится как `decimal(18,2)`.
- Внешние ключи настроены как теневые свойства: в доменных классах есть только навигационные свойства (`Order.Client`, `Item.Category`), а колонки `ClientId`, `ItemId` и `CategoryId` существуют только в модели EF. Доменная модель не зависит от способа хранения.
- Для всех связей задано `DeleteBehavior.Restrict` (`ON DELETE NO ACTION`): база не даст удалить клиента или изделие с заказами либо категорию с изделиями.
- Даты хранятся в UTC. При чтении конвертер помечает их как `DateTimeKind.Utc`, поэтому API возвращает даты с суффиксом `Z`.

Миграция `Initial` создаёт таблицы и заполняет их данными из `TestData` через `HasData`: 10 клиентов, 10 категорий, 20 изделий и 20 заказов. В режиме Development API применяет недостающие миграции при запуске.

Репозитории загружают связанные данные через `Include`: изделия — вместе с категорией, заказы — вместе с клиентом, изделием и категорией изделия (`ThenInclude`). Если база отклоняет операцию из-за связанных данных (например, связанная запись удалена одновременно с запросом), контроллер возвращает `409 Conflict`.

Новая миграция создаётся из папки `DryCleaning` командой:

```powershell
dotnet ef migrations add <Название> --project src/DryCleaning.Infrastructure.EfCore --output-dir Data/Migrations
```

## Оркестрация

`DryCleaning.AppHost` описывает три ресурса:

| Ресурс | Что это |
|---|---|
| `sql` | Контейнер MS SQL Server. Контейнер постоянный (`ContainerLifetime.Persistent`), данные хранятся в томе Docker и сохраняются между запусками |
| `drycleaning` | База данных внутри `sql` |
| `api` | Проект `DryCleaning.Api` |

API получает строку подключения через `WithReference(db)` — в переменной окружения `ConnectionStrings__drycleaning` — и запускается только после готовности базы (`WaitFor(db)`). Контекст регистрируется клиентской интеграцией Aspire `AddSqlServerDbContext`. `DryCleaning.ServiceDefaults` подключает проверки состояния и телеметрию, поэтому логи, трассировки и метрики API видны в дашборде Aspire.

## DTO и проверки данных

| Сущность | Ответ API | Создание | Изменение |
|---|---|---|---|
| Клиент | `ClientDto` | `ClientEditDto` | `ClientEditDto` |
| Категория | `ItemCategoryDto` | `ItemCategoryEditDto` | `ItemCategoryEditDto` |
| Изделие | `ItemDto` | `ItemEditDto` | `ItemEditDto` |
| Заказ | `OrderDto` | `OrderCreateDto` | `OrderEditDto` |

DTO заказа содержит `ClientDto` и `ItemDto`, а DTO изделия — `ItemCategoryDto`. Доменные сущности из API не возвращаются.

Входные DTO используют атрибуты валидации. Имя клиента ограничено 100 символами, телефон — 20 символами и проверяется атрибутом `[Phone]`. Название категории ограничено 50 символами, цена должна быть больше нуля и не превышать 10 000 000. Название и материал изделия ограничены 100 символами. Идентификаторы связанных записей и плановый срок обработки должны быть положительными, виды обработки и статусы — допустимыми значениями enum.

Существование связанных записей, запреты удаления и соответствие даты завершения статусу заказа проверяются в сервисах. Ошибки выполнения операций записываются через `ILogger`; при неожиданной ошибке контроллер возвращает `500` без внутренних деталей исключения.

## REST API

Для каждой сущности доступны `GET` списка, `GET` по ID, `POST`, `PUT` по ID и `DELETE` по ID.

| Сущность | Список и создание | Получение, изменение и удаление по ID |
|---|---|---|
| Клиенты | `/api/clients` | `/api/clients/{id}` |
| Категории | `/api/categories` | `/api/categories/{id}` |
| Изделия | `/api/items` | `/api/items/{id}` |
| Заказы | `/api/orders` | `/api/orders/{id}` |

Заказы ссылаются на существующих клиентов и изделия, а изделия — на существующие категории. Нельзя удалить клиента или изделие с заказами либо категорию с изделиями: сервер возвращает `409 Conflict`. Для некорректных данных используется `400 Bad Request`, для отсутствующей записи — `404 Not Found`. Успешное создание возвращает `201 Created`, а изменение и удаление — `204 No Content`.

Новый заказ получает статус `Accepted` и время приёма в UTC. При изменении заказа дата завершения обязательна для статусов `Completed` и `Issued`, а для остальных статусов должна быть пустой. Передаваемая дата завершения должна содержать `Z` или смещение часового пояса и не может быть раньше даты приёма.

Для получения связанных записей доступны:

- `GET /api/clients/{clientId}/orders` — заказы клиента;
- `GET /api/categories/{categoryId}/items` — изделия категории.

Если клиент или категория существуют, но связанных записей нет, возвращается `200 OK` с пустым массивом. Если клиент или категория не найдены — `404 Not Found`.

## Аналитические запросы

| Маршрут | Результат на исходных данных |
|---|---|
| `GET /api/orders/in-progress` | Заказы в обработке, отсортированные по дате приёма: ID 1, 12, 9 |
| `GET /api/clients/top?start=2025-09-15&end=2026-09-15` | Пять клиентов по числу принятых изделий: ID 1, 2, 3, 4, 5; количества 4, 4, 3, 2, 1 |
| `GET /api/clients/top-spender` | Клиент 2, сумма выданных заказов 6700 |
| `GET /api/clients/longest-processing` | Клиенты 1 и 4, максимальная длительность 19 дней |
| `GET /api/categories/popularity?end=2026-03-01` | Наиболее популярные категории: ID 8, 3, 6, 4, 1; наименее популярные: ID 2, 9, 3, 6, 4 |

Результаты получены на данных, которыми миграция заполняет базу. В запросах за период начальная дата включается, конечная — нет. Для рейтинга клиентов параметры `start` и `end` обязательны; отсутствие любого из них возвращает `400 Bad Request`. Отменённые заказы не участвуют в рейтингах клиентов и категорий. Категории без заказов участвуют в рейтинге наименее популярных. Расходы клиента считаются по текущей цене категории изделия.

## Запуск и проверка

Требуются .NET SDK 10 и запущенный Docker Desktop. Из папки `DryCleaning` запустить оркестратор:

```powershell
dotnet run --project .\src\DryCleaning.AppHost
```

В Visual Studio можно открыть [DryCleaning.slnx](DryCleaning.slnx), выбрать `DryCleaning.AppHost` запускаемым проектом и нажать F5.

В консоли появится ссылка для входа в дашборд Aspire. При первом запуске Docker скачивает образ SQL Server, это занимает несколько минут. Когда ресурсы `sql`, `drycleaning` и `api` перейдут в состояние Running, API доступен по ссылке из дашборда (`https://localhost:3622`). Swagger UI находится по адресу `https://localhost:3622/swagger`, описание OpenAPI — `https://localhost:3622/openapi/v1.json`.

Для ручной проверки открыть [DryCleaning.Api.http](src/DryCleaning.Api/DryCleaning.Api.http). Там собраны успешные запросы и примеры ошибок. Запросы на изменение и удаление созданных записей используют идентификаторы 11 и 21, которые база выдаёт первыми после начальных данных. Поэтому файл рассчитан на однократный прогон по порядку на только что созданной базе.

Для запуска пяти тестов xUnit v3 из той же папки:

```powershell
dotnet test .\DryCleaning.slnx
```

Тесты проверяют аналитические LINQ-запросы на фиксированном наборе данных `TestData`. Им не нужны база данных и Docker.
